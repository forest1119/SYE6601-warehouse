# 07A 接口草案 0.1

## 输入为评分投影

`score_snapshot(snapshot, policy=None)` 接收一个快照。它不是全组的原始证据主表，不要求团队删除或改名原字段。02B/03A应从团队主模型明确选择或映射字段后传入；不得按来源名字自动推断命题、关键性和有效性。

原始证据仍须保留项目要求的 customer_id、scope、version、effective_from/to、fetched_at、tool_status、pagination_complete、citation 等元数据。当前投影用 checks 承接 Checker 的判定，用 evidence_id 与 snapshot_id 回查完整记录，不在评分层重复实现时间、客户和版本判断。

| 字段 | 含义与负责人 |
|---|---|
| schema_version | 固定 `0.1-draft` |
| task_id / run_id / snapshot_id | 任务、一次方法运行、该运行中的证据快照；同一运行补查后生成新快照 |
| rules_version | 本次使用的业务规则版本，由01A/02B提供 |
| synthetic_demo | 是否演示数据；真实联调不得混入手写演示输出 |
| checker_decision | RECOMMEND_COMPENSATION / DO_NOT_RECOMMEND / UNDETERMINED，由02B提供 |
| process_state | RUNNING / COMPLETED / ESCALATED，由03A提供 |
| stop_reason | 运行中可为null，停止/升级必须说明原因 |
| obligations | 本次已建模的全部相关义务，不能只传已查到的项目 |
| evidence | 可引用证据的轻量索引；ID、source_type、citation |

## 每项义务

| 字段 | 说明 |
|---|---|
| obligation_id / rule_id | 稳定标识。重复ID拒收，编号不能依赖随时变化的数组位置 |
| statement | 清楚的单项待证明命题，由01A定义 |
| applicability | APPLICABLE / NOT_APPLICABLE / UNDETERMINED |
| applicability_reason | 为什么适用、不适用或尚不能确定；必填 |
| required_for_decision | 是否为当前判断的必要条件，由业务依赖和Checker确定 |
| must_verify | 即使不改变结论也必须核验的程序要求 |
| status | SUPPORT / REFUTE / UNKNOWN / CONFLICT；NOT_APPLICABLE时必须为null |
| checks | 来源、客户范围、版本、时间、查询充分性五项声明；每项 true/false/null |
| evidence_ids | 引用必须存在于evidence；已查明时不能为空 |
| reason_codes / reason | 原因码列表与人可读解释；未查明时原因码不能为空 |

五项 checks 是 `source_allowed`、`scope_valid`、`version_valid`、`time_valid`、`query_sufficient`。null 表示未核验，false 表示核验不通过。SUPPORT/REFUTE要求五项均true。

`query_sufficient` 不等同于工具HTTP成功。对于“不存在适用记录”的命题，通常要求正确客户、范围和完整分页；对于有直接决定性记录的命题，是否需要全量分页由01A/02B定义。评分器不替代这一判断。

已证明无记录时也需要 evidence_id，引用完整查询的回执；不能凭空造一份合同或用空引用代替。证据索引仅承载引用，具体查询回执由04B/02B保存。

## 状态组合

| applicability | status | 分母 | 门槛 |
|---|---|---|---|
| APPLICABLE | SUPPORT/REFUTE | 计入 | 校验与引用齐全后视为查明 |
| APPLICABLE | UNKNOWN/CONFLICT | 计入 | 关键或必查则阻断 |
| UNDETERMINED | UNKNOWN | 计入 | 阻断，不能当作不适用移除 |
| NOT_APPLICABLE | null | 不计入 | 必须保留不适用解释 |

## 输出评分卡

机器定义见 `schemas/scorecard.schema.json`，三个完整样例见 `examples/*.scorecard.json`。

- 原样关联 task/run/snapshot/rules 版本及演示标记。
- score、raw_score、scoring_policy_version、policy_status说明分数与策略。
- gate_passed、may_present_definitive_decision为独立布尔值，UI不能从分数反推。
- blockers是必须优先显示的阻断项；gaps列出所有仍未查明义务，包括非关键缺口。
- obligations给出逐项分母、查明状态、引用、适用性解释。
- evidence保留来源和引用的轻量索引，08B只读评分卡也能展示出处；完整元数据仍回查上游快照。
- dimensions给出每项校验通过数和分母，不是附加权重。
- 不产生下一步工具名、不变更 Checker 决定、不替 Loop 决定升级。

08B展示顺序建议：Checker结论/流程 → blockers → score与“非概率”说明 → 分项 → 证据引用。发生 ContractError 时清除当前评分显示并展示错误，不能复用旧分数。

## 策略与错误

`policy.demo.json` 是显式可传的演示策略，与默认策略一致。修改权重体系需要新设计；首版仅允许调整阻断上限和策略版本/状态。升到 TEAM_CONFIRMED 之前应保存团队确认记录，程序本身无法证明已获确认。

缺字段、枚举错误、无效数字、重复ID、悬空引用、无证据却声明查明、Checker确定结论与必要缺口冲突，均抛出 ContractError。错误是接口/上游逻辑问题，不应伪装成一个低分业务样本。

JSON Schema只检查结构；跨字段约束和引用约束仍必须调用程序校验。不要只验证Schema就认定输入语义正确。
