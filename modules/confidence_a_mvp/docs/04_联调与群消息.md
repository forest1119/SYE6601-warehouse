# 联调清单与群消息

## 先找谁

1. 02B：共同将一份真实Checker结果投影为snapshot，先试通评分。
2. 08B：读取三个现成scorecard，把阻断原因放在分数前面。
3. 01A/产品经理：确认命题、关键性、适用性、回退和空结果语义。
4. 05A/06B：确认独立评审字段，再接入真实运行结果。
5. 03A/04B：补查后更新快照；保留分页、权限、耗时和成本轨迹。

## 验收

- 三个样例能显示100/100/49，且第二个明确是不补偿。
- 第三个虽然原始分80，仍不能给确定结论。
- 缺字段、悬空引用、关键未知却给确定结论，界面显示输入错误，不显示旧分数。
- 补查后调用方使用新的snapshot_id重新评分，旧轨迹仍可查看。
- 同一案例两个方法证据不同，独立支持性评审可以不同。
- 演示数据始终标记，正式报告不引用手写指标。

## 可发到群里的消息

我这边07A独立最小模块已经搭好：提供评分函数、JSON接口草案、三个输入/输出样例和自动测试。分数表示证据充分性，SUPPORT/REFUTE都可算查明，关键未知会阻断，不用分数代替业务结论。

想先和02B对齐一份Checker快照，和08B对齐评分卡。01A麻烦确认每项待证明命题、ID、关键/必查条件和空结果规则；目前样例是联调占位，没有替你们推断正式业务定义。

05A/06B这边希望逐次运行记录带上独立评审：实际回答时取得的证据是否足够，不能只给案例固定的“证据充分”标签；同一个案例不同方法拿到的证据可能不同。调用、费用、耗时缺测用null，模拟和真实实验分开标记。

下次会建议先走通“缺合同→补查→改判”一个案例，再冻结接口。待确认业务规则和评分参数已经单独列在docs/03_待团队确认.md，展示上限49只是演示参数，不是已确认标准。
